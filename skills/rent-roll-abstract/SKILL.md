Use this skill when the user asked for unit counts, occupancy, vacant, MTM, or in-place income — including when the same message also asks locate/map. Forward occupancy / expirations / predicted income is `ask_prediction_agent` (rr-predict), not this skill. Which floor plan is more likely vacant, or the probability a unit type is vacant, is one `ask_vacancy_agent` call. Cite the probabilities it returns. A vacant headcount stays `query_units`. Ignore it only for a locate/map question with no count/occupancy/income ask (including a last-pin country/place correction or search-the-map follow-up — still this roll; last User message wins; never the need-file sentence when VAULT HAS). Buy / worth THIS deal uses underwriting (`compute_income` / `compute_noi`). Average property value in that area / metro / comps / area/market facts uses underwriting `web_search`, not this skill — do not refuse them and do not ask for a spreadsheet for that ask. Talking to the agent as a person or idle chat is out of scope — refuse with the system-prompt sentence, no `create_plan`, no vault tools. Idle weekend weather is OOS; facts about the property's area or market stay in scope. Cite span_ids. Do not invent rents. Do not geocode or web-search on a pure abstract. Never copy `(skill)` into the user-facing sentence.
`in_place_monthly` is occupied-only. If all occupied / 100% occupancy / fill-vacancy income is a different question — call `compute_income` and cite `estimated_full_occupancy_monthly`; do not repeat occupied in-place. Follow-ups must answer the last user message (including “but this is the same as with vacancy”).
One unfiltered `query_units` JSON returns `unit_count`, `occupied_count`, `vacant_count`, `occupancy_pct`, and `mtm_count` (units on month-to-month leases) plus a note that those headline counts are complete in that result. If several checklist intents are headline counts (units, occupancy, vacant, mtm_count), that is ONE unfiltered `query_units` item, not four. After an unfiltered `query_units` has run this turn, do not call `query_units` again for those counts. Extra `query_units` only to LIST a filtered subset of unit rows, not to re-fetch counts. `compute_income` still for in-place monthly $. `compute_income` JSON also includes `mtm_count`. Use counts for existence/yes-no. `query_units` filters unit occupancy status only (Occupied/Vacant/all).
Always `create_plan` once first with **one numbered line per needed work tool**, not per comma in the user sentence. A one-item list is fine when that one tool answers the whole last message (this-deal occupancy only or vacant-only → `query_units`; definition of a rent roll → `web_search`; create/publish a memo or proceed/yes after a memo ask → the first (and typically only) work tool is `publish_memo` with title+body synthesizing THIS session; NEVER print `functions.publish_memo` JSON or "Let's proceed"; one-item `create_plan` then IMMEDIATELY call MCP `publish_memo` the same turn if possible; do not dump the memo as chat before the tool; do not extra `create_plan` loops; saved memos / vault notes / a published memo already in FACTS → answer only from MEMO# rows (or say none published after HITL); do not call `publish_memo`; do not treat chat history as the vault memo). Only if THIS last message asks map AND MTM AND cap: `1. osm_geocode`, `2. query_units`, `3. compute_cap_rate` — never one comma-joined line, and never copy that three-item list onto a definition or occupancy-only ask. Never `osm_geocode` / `compute_cap_rate` / `compute_noi` unless THIS message asked. Do not re-run prior-session abstract/underwrite tools just because they sit in chat memory. Never call `query_units` (or any work tool) unless it is already on the checklist — if you omitted it, `update_plan` with the missing items first, then that tool. Then the `[in_progress]` work tool, then `update_plan_status`, then the next pending tool. Never skip `create_plan` on in-scope CRE. After `update_plan_status`, if any item is `[pending]` or `[in_progress]` and that tool has not run yet, call that work tool — not `update_plan_status` again. If a tool cannot supply the asked result, mark that item `[incomplete]` (terminal, like `[completed]` but without an answer) and do not retry it. Forbidden: `update_plan_status` → `update_plan_status` except to mark `[completed]`/`[incomplete]` a tool that already ran this run. If remaining items are `[completed]` or `[incomplete]`, Next: `score_gcr` then answer. If `score_gcr` says need_replan because the steps are wrong, call `update_plan` with the NEW remaining work only (never a second `create_plan`). `[completed]` / `[incomplete]` rows stay on the plan.
Forbidden: text-only `end_turn` on a CRE/rent-roll answer with no `score_gcr`. You MUST call `score_gcr(draft)` with the prose sentence you would show before you stop. Do not require RollAbstract JSON. If min(G,C)<=2, need_replan then `score_gcr` again. If the last ask is a CRE definition and the draft was off-topic deal numbers, do not add vault calculators — rewrite a cited definition (`web_search` if needed). `vault_calc` N/A (number not in the vault allowlist, including derived math) is not a fail. Do not return to the user until G/C are ok or you hit the turn limit.
